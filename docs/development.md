# Development

## Running the shell

`make dev` starts the shell and the Lua config from the repository in a nested Hyprland window, without touching the running session. Every keybinding uses `ALT` instead of `SUPER` there, because the outer session captures `SUPER`. For example, `ALT + A` opens the action center.

Its config files live in `build/dev/config`, so saving monitors or a wallpaper does not change the real ones. `settings.json` and `settings.lua` are copied there on the first run. Services such as `hypridle` are not started in a nested session.

## Keybindings

Defaults are in `hypr/binds.lua`, one per line. To change them, create `~/.config/hypr/binds.lua` and list only what differs. Saving the file applies it.

```lua
return {
    { "SUPER + T", act.exec("kitty"), "Terminal" }, -- replaces the default
    { "SUPER + P", false },                         -- disables it
    { "SUPER + B", act.exec("zen"), "Browser" },    -- adds a new one
}
```

A new named action goes in `hypr/lib/actions.lua`.

## Hyprland settings

`~/.config/hypr/settings.lua` runs after the defaults, so anything set there wins:

```lua
hl.config({ input = { kb_layout = "pl" } })
```

An error in a user file appears as a notification, and the defaults still load. `monitors.lua` is generated by the shell; it may be edited, and the display settings write it anew when they save a layout.

## Settings

`~/.config/hyprdora/settings.json` overrides the defaults in `shell/config/Settings.qml`. Every key is optional, and saving the file applies it. The settings button in the action center writes the same file, so everyday settings need no editing. The `"//"` key on top is a note for whoever opens the file and is not a setting.

The shell makes both files when they are missing, at start or after being deleted, with no settings and no rules: watching them for changes needs a file, and a deleted folder would end the watch for good. Deleting one is therefore the same as emptying it, a return to the defaults.

```json
{
  "language": "auto",
  "weather": { "place": "Warsaw", "latitude": 52.23, "longitude": 21.01 },
  "idle": { "dim": 240, "lock": 300, "suspend": 900 },
  "capture": { "systemAudio": false, "microphone": false },
  "terminalCommand": ["alacritty", "--class", "systui", "-e"],
  "brightnessMinimum": 0.016,
  "calendarScrollDelay": 100
}
```

Weather stays hidden until `weather` has coordinates. `idle` times are in seconds, and 0 turns a step off; suspend applies only on battery.

To add a settings category, add an entry to `categories` in `modules/actioncenter/settings/SettingsMenu.qml` and a component that reads `Settings` and saves with `Settings.set` or `Settings.setIn`.

## Adding a language

Copy `shell/i18n/en.json` to `shell/i18n/<code>.json` and translate the values. A missing key falls back to English.

Plurals are objects. Languages with simple plurals need `one` and `other`. If a language needs other forms, add its rule to `pluralRules` in `shell/config/I18n.qml`.

```json
"notifications.count": { "one": "{count} notification", "other": "{count} notifications" }
```

In QML: `I18n.t("notifications.count", { count: 3 })`.

## Code conventions

- English everywhere in the repository: code, comments, Markdown, commit messages.
- One-line comments only where truly needed. They explain why, not what.
- Doc comments on functions: purpose, parameters, return value. JSDoc style in QML/JS, LuaLS `---@param` in Lua, docstrings in Python, a header comment in shell scripts. Required in services, libraries and scripts; trivial signal handlers are exempt.
- Logic that can run in QML is written in QML. Python is used only where QML cannot do the job, and shell only where the desktop is not running.
- Conventional Commits (`feat(shell): ...`), one branch per stage, merged to `main`.
- Documentation changes land in the same commit as the code they describe.
- No dead code: a change that stops using a translation key, an icon, a Theme token, a setting, a function or a file removes it in the same commit. It can always be added back.
- Watching the local system goes through `EventSources` in `shell/base/`, never straight from a module or another service: a process that prints events (`nmcli monitor`), a file watched for changes (`FileView.watchChanges`), or a poll where nothing can be subscribed to. Each source runs once however many listen, starts with its first listener and stops after its last, ends with the shell and restarts if it fails, so a change of tool happens in one place. Subscribing to an event comes before polling it.
- Downloads on a schedule (weather, updates, calendars) run through `ScheduledTask`, which decides when they may run: not while offline, waiting on a metered network unless allowed, catching up once the network returns or after waking. The data stays in the service that owns it.
- A new tool the system needs (a package the spec requires) is the author's decision, with its pros and cons laid out first.

## Tools

`make lint` runs `qmllint`, `qmlformat`, `shellcheck`, `ruff` and `stylua` on the files that exist. Set `QT_BIN` if the Qt tools are not in `/usr/lib64/qt6/bin`.
